# v0.4.0 — The install path stops being theoretical

v0.3.0 shipped a desktop app in front of a workflow that could plan a queue but
had never finished one automatically, and whose removal half turned out not to
work at all. This release closes both, and verifies the result against real
hardware rather than against test doubles.

- The automatic path now resolves a complete plan for the Brother HL-L2315D.
  The Windows driver name was confirmed on hardware and is bound **per model**,
  not per family: the family covers five models and Brother names drivers per
  model, so a name proven on one is never asserted for a sibling nobody has
  tested. Every other model still fails closed until its own confirmation.
- Removal is reviewable before you grant administrator rights. The preflight now
  runs after the plan is shown, matching install, so you can read exactly what
  would be removed and then decide. The gate itself is unchanged — the mutation
  boundary re-checks elevation.
- Driver staging from the reviewed local Brother archive works on a machine that
  does not already have the driver, verified end to end for the first time.

## Fixed

- **Removal was broken, not merely unverified.** The generated PowerShell emitted
  `PrinterName`/`PortName`/`DriverName` while the struct reading it is tagged
  `printer_name`/`port_name`/`driver_name`. Go's case-insensitive fallback does
  not bridge an underscore, so every real lookup decoded to an empty
  configuration with a **nil error**, and removal failed with either "printer
  name and port name are required" or `installed queue differs from profile
  (port "", driver "")`. An unelevated machine never saw it, because the
  elevation error arrived first.
- **Driver staging resolved `tar` through `PATH`.** The vendor archive is a
  self-extracting EXE only Windows' own bsdtar reads, so on any machine with
  Git, MSYS or Cygwin ahead of System32 — most developer machines — staging
  failed with an error blaming the vendor archive for what was a `PATH` problem.
  It failed closed and mutated nothing, but it misdiagnosed itself. `tar` is now
  resolved to System32 and checked before use.
- The `VERSION` marker still read `v0.2.0` through the whole v0.3.0 cut.

## Verified

Against the operator's live Brother HL-L2315D, in an elevated session:

- Removal deletes the queue, and the port only when nothing else uses it. With a
  second queue on the same port it reported `Retained shared port` and the port
  survived; with the port unshared, `Removed unused SpoolSmith port`. The driver
  survived both, as `--purge-driver` was not passed.
- With the package genuinely deleted from the Windows Driver Store, `add
  --profile` hash-checked the archive, verified Brother's Authenticode
  signature, extracted it, verified the catalog against the Microsoft WHCP
  signer, staged the INF with `pnputil` and registered the driver unattended —
  landing the same `oem15.inf` and the same Driver Store directory as the
  original hand-staged install.
- Both fail-closed paths still refuse: unelevated, and driver-absent. Each shows
  the plan first and then refuses, so an operator can read what would happen
  before granting rights. Both exit 4.

## Requirements and limits

Run as administrator to apply queue changes; finding printers and saving their
settings does not. Most drivers must already be registered locally; the optional
package recipe still supports only the verified Brother model on Windows x64,
and vendor payloads are neither bundled nor downloaded.

**No printed page has confirmed this release.** The last physical print was made
before the driver-staging cycle above, and only paper proves a driver is
correct — a wrong-but-similarly-named driver installs cleanly and prints
garbage. HP LaserJet Pro M4xx remains entirely unverified against hardware and
still fails closed for want of a confirmed driver name. Failures can still leave
partially staged resources.
